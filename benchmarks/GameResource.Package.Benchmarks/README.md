# GameResource.Package workload benchmark

测试当前独立库的公开 API，不修改库的实现。只创建资源包和 JSON 结果，不在文件系统生成 50 万个散文件。

## 运行

从仓库根目录执行：

~~~powershell
powershell -ExecutionPolicy Bypass -File benchmarks/GameResource.Package.Benchmarks/Run-Benchmark.ps1
~~~

需要 .NET 10 SDK。运行脚本采集 Windows 硬件、操作系统、电源计划、库源码 SHA-256 及程序集 SHA-256。每个编码版本的每个阶段在新的子进程内执行，阶段串行运行。结果默认存入新的 artifacts/package-benchmark-* 目录。

可用 Directories、Files 和 Rounds 参数设置规模；Files 必须能被 Directories 和 40 整除。默认 1000 个目录、500000 个文件、3 轮。输出目录必须不存在，以免覆盖先前的测试。

## 数据集

每目录 500 个文件，路径形如 dir0000/file000000.bin，默认完整路径长度为 22 个 UTF-8 字节。基础阶段不包含 Meta，也不加密；modern 阶段随后为每个文件添加 MessagePack Meta。

| 数量 | 比例 | 单文件长度 | 合计 |
| --- | --- | --- | --- |
| 400000 | 80% | 1024 B | 409600000 B |
| 75000 | 15% | 4096 B | 307200000 B |
| 25000 | 5% | 16384 B | 409600000 B |
| 500000 | 100% | 平均 2252.8 B | 1126400000 B |

每个大小类别中，半数内容使用固定种子的随机字节，半数使用重复的 64 字节模式。每个文件的前 8 字节写入独有文件编号和更新版本。这是可复现的合成负载，压缩率不能代表真实图片或脚本资源。

生成 None 与 Auto/LZ4 两个包。每阶段检查包文件总长度低于 3000000000 B。输入数据复用几个小缓冲区，不保留全量原始内容。

## 指标和计时范围

* 创建：分别记录 50 万次 PutFile 和最终 Save；记录完整性校验结果。
* 加载：新进程首次 OpenRead，以及后续 5 次 OpenRead。首轮包含首次使用的运行时/JIT 成本。
* 查找：固定随机顺序的 50 万次 GetEntry。
* 读取：先进行一次不计时的全量读取，再分别测全量顺序读取、全量随机读取，各 3 轮。每次包括按路径打开资源、读取完整内容、校验长度和编号、关闭资源流。
* 范围读取：固定随机顺序的前 10 万个文件，读取最多 4 KiB。1 KiB 文件读取 1 KiB，较大文件读取 4 KiB；包含路径定位和流生命周期。记录单次延迟 P50/P95/P99。
* 枚举：根目录的 1000 个直接目录、全量 50 万文件、逐个目录列出其 500 个直接文件；各 5 轮。遍历结果但不保存为列表。逐目录枚举还记录每个目录的延迟分位数。
* 更新：单文件及一批 10000 个随机文件，分别连续 3 轮。每轮重新 OpenEdit，分别计时打开、首个 PutFile、其余 PutFile、Save。全部为等长内容替换，变化体现在版本字段。每轮后读取并比对更新的全部文件，最后 Verify 全包。

更新使用同一包连续执行，不重置空闲区，因此后续轮次包含空间重用和碎片状态的影响。合成的“更新并保存总时间”是对应阶段测量值的和；包打开时间单列，不包含在该和中。每轮校验和测量记录输出不计入时间。

每个阶段测量前在计时外执行完整 GC，计时区间仍正常包含运行时触发的 GC。记录总托管分配量与 GC 次数。读取/更新的路径数组、随机排列、数据缓冲区均在计时外准备。范围读取和更新的单次延迟包含 Stopwatch 采样开销。

Release 构建、Workstation GC。基础阶段单线程；modern 阶段显式比较 1、4、8 并发。子进程设置 DOTNET_TieredCompilation=0，减少分层编译造成的轮次差异；不修改系统全局配置、电源计划或进程亲和性。

## 缓存和内存解释

**没有清空 Windows 文件缓存。读取结果属于有缓存的端到端 API 性能，不是 SSD 冷读带宽。**“新进程首次打开”也不等同于存储冷启动。

托管分配量是整个操作中累计分配的字节，不能当作常驻内存。open 阶段没有创建 50 万个测试路径字符串，单独记录打开前、打开后以及完整 GC 后的内存，用于估算保留索引的开销。

其他阶段的进程工作集/峰值包括测试程序自己的路径数组、随机排列、GC 堆保留空间和运行时，不能全部归因于库。基础索引字节数来自公开的 PackageStatistics；其数值不包括操作系统文件缓存。

JSON 结果保留每一轮原始数据、样本数、字节数、延迟分位数、内存及机器信息。报告采用重复轮次的中位数，并保留最小/最大值供核对。

## 0.2.0 的 Meta、Async 和懒加载比较

modern 阶段在文件更新测试后执行：为全部文件写入四个字符串键的 Meta（id、width、name、tags），单独记录写入和 Save；比较带 Meta 时的同步/异步打开。

固定抽样 100000 个不同路径的资源，先预热内容及 Meta 的系统缓存，然后禁用库内 Meta LRU，用 DTO 合并读取 Meta+完整内容，分别测同步和原生异步在 1、4、8 并发下的吞吐。同步多路使用 Parallel.For；异步使用固定数量的 async worker，无 Task.Run 包装。每次验证文件编号、Meta 编号及库内部 XXH64，及时释放池化结果。同步串行另测 ResourceProperties。

懒加载引用只测创建 500000 个引用，创建后丢弃，验证其不进行内容 I/O的测试由单元测试负责。热 Meta 场景测同一路径重复读取 100000 次 DTO，开启默认 LRU。

序列化器微基准对相同四字段 DTO 分别进行 1000000 次 MessagePack 和 System.Text.Json 解码（键名一致），均包含对象分配；MessagePack 开启 UntrustedData 和深度 64。微基准不包含磁盘、内容、校验和写入时的 named-map 验证，也不用于推导整个资源加载的倍数。它使用默认 DTO 序列化器配置，没有为 JSON 单独生成 JsonSerializerContext。

最终报告：[0.2.0 / 50 万文件](results/2026-10-25-v02-500k/REPORT.md)。历史报告：[0.1.0](results/2026-10-25-500k/REPORT.md)。所有结果来自合成数据和热系统文件缓存，不代表冷盘延迟。总包数据上限仍为 3 GB；重新运行前应清理自己生成的旧测试包，以免跨输出目录累积超限。
