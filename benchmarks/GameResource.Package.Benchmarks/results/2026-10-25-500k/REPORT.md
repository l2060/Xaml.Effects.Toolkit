# 1000 目录、500000 文件 Benchmark 实测

测试时间：2026-10-25，Asia/Shanghai。测试对象：GameResource.Package 0.1.0；本次没有修改库实现。

## 环境和数据

- Intel Core i7-13700KF，16 核 / 24 线程，64 GiB 内存。
- Windows 11 企业版 10.0.28000，.NET SDK 10.0.401，运行时 .NET 10.0.12，Release x64、Workstation GC、单线程调用。
- D: 为 NTFS，位于 WDC WDS100T2B0B-00YS70 SATA SSD。电源计划为机器原有的“卓越性能”。
- 每个包 1000 个一级目录，每目录 500 文件，共 500000 文件；完整路径为 22 个 UTF-8 字节，例如 dir0000/file000000.bin。
- 400000 × 1 KiB + 75000 × 4 KiB + 25000 × 16 KiB，总原始内容 1126400000 B（1.1264 GB / 1.0490 GiB）。
- 每个大小类别中，50% 是固定种子随机数据，50% 是重复 64 字节模式。文件包含唯一编号和版本，不使用跨文件去重。
- 分别测试 None 与 Auto/LZ4；没有密码加密和 JSON 属性。这个压缩率仅代表此合成负载。
- 子进程局部设置 DOTNET_TieredCompilation=0；每个阶段使用新进程。没有修改系统缓存、电源设置或 CPU 亲和性。

**没有清空系统文件缓存，读取计时前完整预读一次。以下是缓存条件下的端到端 API 性能，不能当作 SSD 冷读性能。新进程首次打开也不等于存储冷启动。**

读取、查找和更新各 3 轮；重复打开、枚举各 5 轮。下表采用中位数。创建和新进程首次打开各测 1 次。数据生成、测试路径数组构造、正确性校验和报告输出均不计入读取/更新耗时。计时前在计时区间外执行完整 GC。

## 数据反映出的成本

1. 当前全量索引打开约 0.75 秒。源码中的 CompactIndex.Load 对每条 64 字节记录单独读取、校验路径并创建临时对象；单次打开累计分配约 174.6 MiB，高于约 41 MiB 的保留索引。
2. 首次修改需要将 50 万条紧凑记录转换为可编辑集合，额外保留约 103 MiB。Save 重写完整索引，因此单文件修改也承担约 1.4–1.5 秒的“初始化编辑集合 + 保存”成本。批量保存可以摊薄这项成本。
3. 根目录虽然仅返回 1000 个目录，当前 Enumerate 仍扫描所有 50 万记录并分配约 99 MiB。全文件枚举每轮累计分配约 103 MiB；频繁枚举会增加 GC 压力。
4. 本次热缓存负载下，LZ4 包更小，但分块描述读取和解码使顺序/随机读取较 None 更慢。这个结果不能推出冷盘、不同资源大小或真实压缩素材上的表现。

没有进行性能修复，也没有测试加密、JSON 属性、真实磁盘冷缓存和其他文件大小分布。
