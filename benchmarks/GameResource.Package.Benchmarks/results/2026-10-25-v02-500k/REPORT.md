# GameResource.Package 0.2.0：50 万文件性能与 API 验证

2026-10-25，Windows 11 / i7-13700KF / 64 GiB / WD SATA SSD，.NET SDK 10.0.401，Release、Workstation GC、DOTNET_TieredCompilation=0。原始环境、源码 SHA-256 和每轮测量均保存在本目录。

本轮实现了并行读/独占写、原生异步读取、独立 MessagePack Meta、合并读取结果、流及应用层懒加载引用。69 项测试通过，包括加密并发读、取消/失败后重试、结果独立释放、缓存失效、Meta 懒读、写入排斥读取和三种提交中断恢复。

## 数据和测量边界

1000 目录 × 500 文件；80% 1 KiB、15% 4 KiB、5% 16 KiB，原始内容 1,126,400,000 B。每类一半随机字节、一半可压缩重复模式，None 与 Auto/LZ4 两个包，无密码加密。读前预热 Windows 文件缓存，**这些数据不是冷盘延迟**。

基础阶段与 0.1.0 使用相同负载和测量方式；随后给全部文件加 Meta，再测合并读取。最终 None 包 1,240,875,184 B，LZ4 包 709,333,024 B，总计 1,950,208,208 B（1.95 GB）。正式运行阶段观察到的最大包数据总量 1,977,082,128 B；另保留 7,277,096 B 的小规模测试包，合计仍低于 3 GB。旧格式/调试测试包已删除，历史测量报告保留。

下表取重复轮次的中位数，读取通常 3 轮，打开/枚举 5 轮。首次进程打开单独记录，不混入重复打开中位数。平均单资源时间是批量总时间除以次数，不是分位数。

## 与 0.1.0 对比

| 操作 | 0.1.0 None | 0.2.0 None | 0.1.0 LZ4 | 0.2.0 LZ4 |
| --- | ---: | ---: | ---: | ---: |
| 打开 50 万记录包 | 748 ms | 221 ms | 753 ms | 224 ms |
| 顺序完整读 50 万文件 | 902 ms | 899 ms | 1334 ms | 1438 ms |
| 随机完整读 50 万文件 | 2113 ms | 2100 ms | 2562 ms | 2622 ms |
| 枚举全部文件 | 17.6 ms | 17.5 ms | 17.8 ms | 17.9 ms |
| 更新 1 文件并保存，不含打开 | 1513 ms | 866 ms | 1425 ms | 775 ms |
| 更新 10000 文件并保存，不含打开 | 1629 ms | 1033 ms | 1609 ms | 994 ms |

打开明显减少的主要原因是索引记录批量 I/O，保存也改为批量写索引。Meta 独立存储使保存不必再复制全包属性。

同步随机完整读取平均 **None 4.20 μs / LZ4 5.24 μs**，包括路径定位、开流、完整读取和释放。低层流没有额外全文件 XXH64 校验；下文 ReadResource 合并读取包含该校验。

最多 4 KiB 的随机范围读取（10 万样本）：None 的 P50/P95/P99 中位数为 3.5/7.5/10.8 μs；LZ4 为 4.5/8.5/12.0 μs。范围读取与完整读取是不同样本，不能混用分位数。

这些改动没有让所有场景都更快：本机 LZ4 顺序读取比历史记录慢约 8%，随机完整读取慢约 2%。这是同机不同时间的测量，不是严格的并排 A/B；没有将差异全部归因于某一实现细节。

首次进入编辑状态仍需构建完整可编辑集合。单文件更新的首次 PutFile 中位数约 666 ms（None）/559 ms（LZ4），仍是需要后续优化的成本。Save 重写索引，不重写全部内容，但并非 O(1)；不要逐个文件修改后立即 Save。

## 同时读取 Meta + 内容

每个文件包含 `{ id, width, name, tags }` 的 MessagePack map。固定随机抽样 100000 个文件，读取前预热系统缓存，禁用库内 Meta LRU，读取强类型 DTO + 完整内容，校验编号和内容 XXH64，立即释放每个结果。

| 模式 | 并发数 | None 总耗时 | LZ4 总耗时 |
| --- | ---: | ---: | ---: |
| 同步 | 1 | 763.9 ms | 856.9 ms |
| 同步 | 4 | 1010.7 ms | 1104.0 ms |
| 同步 | 8 | 1030.2 ms | 1158.3 ms |
| 异步 | 1 | 1694.5 ms | 2216.4 ms |
| 异步 | 4 | 553.6 ms | 709.8 ms |
| 异步 | 8 | **455.2 ms** | **554.5 ms** |

同步单路平均约 7.64/8.57 μs。异步 8 并发的吞吐约 219680/180330 个资源每秒；并发总耗时除以数量只代表吞吐折算，不能解释为单个请求的延迟。

本负载下异步 8 并发相对同步单路约快 1.68/1.55 倍，而异步单路更慢。同步多线程也没有带来收益：Windows 对同一个同步句柄的 I/O 有串行化成本。库允许并发读调用并保证各流位置独立，但不保证同步调用按线程数加速。建议小文件热读用同步；需要并发等待时从 Async 4–8 并发开始测量。

库对同步读使用同步句柄；只有实际需要异步 I/O 时才建立异步句柄，写入前释放第二句柄。这样保留同步小文件性能，避免长期双句柄对本机写入造成的额外成本。资源读取不使用 Task.Run。

ResourceProperties 合并同步单路总时间为 792.8/889.9 ms，比对应 DTO 稍慢，且每 10 万次累计分配约 157/162 MiB；DTO 约 92/97 MiB。异步 8 并发的累计分配约 222/264 MiB，包含异步状态与结果对象，**不是常驻内存**。

## Meta 格式、懒加载和内存

同一 DTO 的示例编码：MessagePack **44 B**，JSON **64 B**。100 万次纯解码：MessagePack 约 208–215 ms，System.Text.Json 约 709–713 ms；累计分配分别约 183/717 MiB。本例 MessagePack 约快 3.3–3.4 倍，不能推广成所有资源加载都快同样倍数。JSON 使用默认 DTO 反序列化器，未添加专门的 JsonSerializerContext；微基准不包含磁盘和校验。

开启默认 Meta 缓存后，同一路径读取 100000 次 DTO：约 66 ms，即每次 0.66 μs。该数据是热 Meta 缓存命中，不代表从磁盘首次加载。

创建 500000 个懒加载引用约 154 ms（约 0.31 μs/个），累计分配约 91.6 MiB。本测试创建后丢弃引用，不表示保留 50 万个引用只消耗很少内存。引用创建没有内容/Meta I/O、没有加载 Task 或完整内容缓冲；只有 Load/Open/GetMetadata 才读取。

同一引用重叠的 LoadAsync 经单元测试验证会合并读取，结果具备独立释放句柄和独立 DTO；单个取消不影响其余等待者。全量内容不进入永久缓存，Meta 使用字节数及项数双上限的 LRU。已有结果可跨修改和包关闭存活；尚未加载的引用按原路径重新解析。

基础索引 43,000,000 B（41.0 MiB），打开并 GC 后托管保留增量约 41.2 MiB；打开时累计分配约 174.6 MiB，仍包含路径/空间校验的临时对象。独立 Meta 不增加每条索引的 64 字节结构，也不在打开时读取 Meta 数据；空间区间校验会增加临时工作量。

带全部 Meta 时 modern 阶段的打开记录约 272–283 ms，但**计时包含 GetStatistics 的全表枚举及“缓存为零”断言**，不能与上面的纯 OpenRead 直接比较。其验证结论是打开之后 Meta 缓存仍为零。Meta 损坏不阻止开包、路径查询或纯内容读取，读取 Meta/Verify 才报错，已有专门测试。

每次缓冲读取默认限制 32 MiB；这是单结果上限，不是所有并发加载的总内存上限。大文件应使用 OpenResource 流，应用应控制同时加载的数量。本轮未测冷盘、加密性能、大文件、SSD 队列饱和或图像解码/GPU 上传。
