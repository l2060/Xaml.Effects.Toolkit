# .NET 10 Zlib 与 LZ4 解压实测

测试日期：2026-10-25。结论针对这次样本和这台机器：按资源库使用的 64 KiB 独立分块，Zlib Optimal 的文本解压耗时约为 LZ4 的 **2.37–2.45 倍**；两张真实图片解码成 32 位像素后分别是 **3.18 倍、6.11 倍**；合成透明精灵图集只有 **1.26 倍**。整张精灵图集压缩时，Zlib Optimal 在本次测试中反而更快约 10%。

因此不能给 Zlib 一个固定的“慢多少倍”，也不能只根据算法名称决定所有图片的默认压缩策略。

## 环境和方法

- CPU：Intel Core i7-13700KF，64 GiB 内存，Windows 11；只将基准进程固定在逻辑 CPU 0，不修改系统设置。
- .NET 10.0.12、SDK 10.0.401、Release x64、Workstation GC，DOTNET_TieredCompilation=0。
- LZ4：K4os.Compression.LZ4 1.3.8，LZ4Level.L00_FAST，与当前资源库默认编码一致。
- Zlib：.NET 内置 System.IO.Compression.ZLibStream，分别用 CompressionLevel.Fastest、Optimal 生成输入；解码使用相同的 ZLibStream API。
- 7 轮，63 个组合、441 条测量。每项预热并校准每轮约 200 ms，固定迭代数；每轮随机排列测试项目。表中耗时是“每轮平均每操作耗时”的中位数。
- **计时仅包含内存中的解压公开 API 调用**：压缩输入已经准备好，输出缓冲区预分配并复用。不包含磁盘、PNG 解码、加密、资源路径查找或资源库内容哈希。
- Zlib 计时包含每单元 MemoryStream / ZLibStream 的创建、解压、流末尾检查、释放及 Zlib 自身校验；LZ4 检查解码长度，不额外增加校验算法。测的是在 .NET 中实际使用这些 API 的成本，不是剥离全部框架和校验开销的裸算法极限。
- 每项预热后和每轮完成后都逐字节对比完整输出，所有内容验证通过。结果 `Completed=true`。

## 64 KiB 独立分块：强制解码

图片全部转为原始 **BGRA32，每像素 4 字节，不预乘 Alpha**；无 PNG 行滤波、通道拆分或其他预处理。下表是解压整个样本的耗时，样本包含多个独立块。

| 数据 | 原始大小 | LZ4 | Zlib Fastest | Zlib Optimal | Optimal / LZ4 耗时 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 真实 C# / XAML 文本 | 1.072 MiB | 0.298 ms | 0.863 ms | 0.729 ms | **2.45×** |
| JSON 资源配置 | 2.333 MiB | 0.395 ms | 1.197 ms | 0.935 ms | **2.37×** |
| 32 × 32 实际图标 | 4 KiB | 1.08 μs | 5.01 μs | 5.51 μs | **5.12×** |
| 733 × 533 实际背景图 | 1.490 MiB | 0.719 ms | 2.583 ms | 2.287 ms | **3.18×** |
| 2560 × 1440 实际背景图 | 14.063 MiB | 2.338 ms | 13.677 ms | 14.284 ms | **6.11×** |
| 1024 × 1024 合成透明精灵图集 | 4 MiB | 0.420 ms | 0.769 ms | 0.529 ms | **1.26×** |
| 1024 × 1024 合成噪声纹理 | 4 MiB | 0.159 ms | 8.951 ms | 9.888 ms | **62.26×，见下文特殊说明** |

Fastest 是压缩速度选项，不保证解压更快。此处文本、733 × 533 背景和透明精灵图集的 Optimal 解压比 Fastest 更快；不同压缩结果的字面量、匹配和编码布局会影响解压路径。

## 速度对应的体积收益

以下是编码后字节数 / 原始字节数，越低越省空间。包含 Zlib 自身头部和校验值；两种算法都不含资源包块表。

| 数据 | LZ4 | Zlib Fastest | Zlib Optimal |
| --- | ---: | ---: | ---: |
| 真实文本 | 25.55% | 22.70% | **15.26%** |
| JSON 配置 | 19.57% | 16.54% | **10.16%** |
| 图标 | 50.73% | 41.06% | **25.15%** |
| 733 × 533 背景 | 72.88% | 57.34% | **33.84%** |
| 2560 × 1440 背景 | 30.41% | 31.13% | **25.13%** |
| 透明精灵图集 | 5.97% | 5.82% | **2.39%** |
| 噪声纹理 | 100.35% | 102.05% | **75.33%** |

这说明 .NET 内置 Zlib 在本次数据中有明确价值。例如 4 MiB 透明精灵图集，Optimal 只比 LZ4 多约 **0.11 ms**，却将存储从约 **244.4 KiB** 降到约 **97.8 KiB**；不能只看速度倍数忽略绝对成本和体积收益。

### 噪声纹理：不能把回退拷贝当作压缩算法优势

在这个高噪声样本中，LZ4 无法有效压缩，强制输出几乎全部是字面量，解码接近复制；Zlib Optimal 则实际把数据压到 75.33%，执行了更多解码工作。因此表中 62.26× 不适合推广到其他图片。

应用当前库的“编码长度大于等于原长度则保存原始块”规则后：

| 策略 | 回退块数 | 实际存储占比 | 整图恢复耗时 |
| --- | ---: | ---: | ---: |
| LZ4 Auto | 64 / 64 | 100% | 0.141 ms，全部内存复制 |
| Zlib Fastest Auto | 64 / 64 | 100% | 0.140 ms，全部内存复制 |
| Zlib Optimal Auto | 0 / 64 | 75.33% | 9.896 ms，执行解压 |

这里 LZ4 与 Fastest 的实际读取路径相同。Optimal 用额外 CPU 时间换取约 24.7% 体积节省；实际磁盘读取是否值得，需在目标存储设备上另测。本轮不包含磁盘，不能直接推导冷加载速度。

其他样本的所有块均压缩成功，Auto 没有触发原始块回退；原始 JSON 另外保存了它们的 Auto 测量。

## 整个样本一次压缩：补充对比

| 数据 | LZ4 | Zlib Optimal | Optimal / LZ4 耗时 |
| --- | ---: | ---: | ---: |
| 真实文本 | 0.263 ms | 0.628 ms | 2.39× |
| JSON 配置 | 0.384 ms | 0.847 ms | 2.21× |
| 图标 | 1.08 μs | 5.37 μs | 4.97× |
| 733 × 533 背景 | 0.343 ms | 2.325 ms | 6.78× |
| 2560 × 1440 背景 | 1.949 ms | 14.647 ms | 7.51× |
| 透明精灵图集 | 0.378 ms | **0.339 ms** | **0.90×** |
| 噪声纹理（强制解码） | 0.148 ms | 9.587 ms | 64.61× |

透明精灵图集整张压缩时，Zlib Optimal 中位耗时比 LZ4 少约 10.4%，存储占比也更低（2.12% 对 4.74%）。7 轮平均单次耗时范围：Zlib 0.325–0.344 ms，LZ4 0.368–0.394 ms。

整张压缩与独立分块改变字典历史、压缩后的匹配形式以及流的初始化次数，不能把两张表混在一起求平均倍数。整个文本样本是源文件连接后的字节，不等同于对每个小文件独立压缩。

## 对当前资源库的建议

- 对频繁随机加载的小资源，LZ4 的低解码/对象开销依然有利。4 KiB 图标的绝对差约 4.4 μs；是否值得用更大文件体积换取这点差异，应看每帧资源量。
- 文本配置及带大面积透明/重复像素的资源，Zlib Optimal 值得作为体积优先选项；本次透明图集的速度差很小，整张布局甚至更快。
- 复杂纹理需要实测。不能把所有 32 位图片都归成同一种性能特征，也不应根据一个噪声样本直接宣称 Zlib 普遍慢几十倍。
- 这次比较不包含写入/压缩耗时，也没有给原生 Zlib 设计可复用上下文。ZLibStream 在每个独立压缩单元上创建/释放的托管成本属于当前公开 API 使用方式。

在预分配输出缓冲区的前提下，LZ4 解码计时内托管分配为 0；Zlib 每个独立单元约 344 B，因此 225 块背景图每次累计分配约 77400 B。不包含原生分配和提前分配的输出缓冲，不能当作总内存占用。
